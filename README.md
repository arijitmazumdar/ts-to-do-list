# TypeScript Todo List

This repository is a learning project for building a complete to-do application with a TypeScript HTTP API, SQLite persistence, and an HTMX user interface. This document is the implementation plan: follow the milestones in order and do not move to the next milestone until the listed verification passes.

## Final application

When complete, the application will let a user:

- create, view, edit, and delete a task;
- list tasks and filter them by status or tag;
- record planned and actual start/end dates;
- start, pause, resume, complete, or cancel a task;
- explain why a task is paused;
- assign tags;
- link related tasks;
- create parent/child task relationships; and
- use either a JSON REST API or a progressively enhanced HTMX interface.

This guide uses one opinionated stack so that every step has a clear implementation:

- Node.js 24 (the exact version is in `.nvmrc`)
- TypeScript in strict mode
- Express 5 for HTTP routing
- `better-sqlite3` for SQLite access
- Zod for request validation
- Nunjucks for server-rendered HTML fragments and pages
- HTMX for browser interactions
- Vitest and Supertest for automated tests
- ESLint and Prettier for static checks and formatting

## Domain contract

Use camel case in TypeScript and JSON, and snake case only in SQLite. A complete task returned by the API has this shape:

```ts
type TodoStatus =
  | 'planned'
  | 'in_progress'
  | 'paused'
  | 'completed'
  | 'cancelled';

interface Todo {
  id: number;
  name: string;
  description: string | null;
  plannedStartDate: string | null;
  plannedEndDate: string | null;
  actualStartDate: string | null;
  actualEndDate: string | null;
  lastUpdatedDate: string;
  latestStatus: TodoStatus;
  isPaused: boolean;
  reasonForPause: string | null;
  tags: string[];
  relatedTaskIds: number[];
  childTaskIds: number[];
  parentTaskId: number | null;
}
```

All dates are ISO 8601 strings. Calendar dates submitted by a user use `YYYY-MM-DD`; timestamps generated by the server use UTC, for example `2026-10-11T08:30:00.000Z`.

Apply these business rules in the service layer, not just in the UI:

1. `name` is trimmed and must contain 1–200 characters.
2. `description` is either `null` or at most 5,000 characters.
3. An end date cannot be earlier than its matching start date.
4. `isPaused` is derived from `latestStatus === 'paused'`; clients cannot set it independently.
5. `reasonForPause` is required for `paused` tasks and must be `null` for every other status.
6. The first transition to `in_progress` sets `actualStartDate`; resuming a paused task preserves it.
7. Changing a task to `completed` sets `actualEndDate` when it is absent. A task must have an actual start date before it can be completed.
8. Task relationships cannot point to the task itself. A related-task link is symmetric and unique.
9. A task can have at most one parent, and parent/child links must not create a cycle.
10. Tags are trimmed, lower-cased, deduplicated, and limited to 50 characters each.
11. Updating or deleting an unknown task returns `404` rather than silently succeeding.

Use this lifecycle state machine. Attempts to make any other transition return `422`:

| Current status | Allowed next status |
| --- | --- |
| `planned` | `in_progress`, `cancelled` |
| `in_progress` | `paused`, `completed`, `cancelled` |
| `paused` | `in_progress`, `cancelled` |
| `completed` | none (terminal) |
| `cancelled` | none (terminal) |

Resuming a paused task means changing it to `in_progress`. Its original `actualStartDate` remains unchanged, and its pause reason is cleared. New tasks always begin as `planned`; status and actual dates are server-managed lifecycle fields.

## HTTP contract

The server listens on `HOST` and `PORT`, defaulting to `127.0.0.1:3000`. JSON routes live under `/api`; HTML routes live under `/`.

| Method | Route | Purpose | Success |
| --- | --- | --- | --- |
| `GET` | `/health` | Process/database readiness | `200` |
| `GET` | `/api/todos` | List tasks; accepts `status` and `tag` query filters | `200` |
| `POST` | `/api/todos` | Create a task | `201` |
| `GET` | `/api/todos/:id` | Get one task | `200` |
| `PATCH` | `/api/todos/:id` | Update supplied fields | `200` |
| `DELETE` | `/api/todos/:id` | Delete a task and its links | `204` |
| `POST` | `/api/todos/:id/related/:relatedId` | Add a symmetric related-task link | `204` |
| `DELETE` | `/api/todos/:id/related/:relatedId` | Remove a related-task link | `204` |

`POST /api/todos` accepts `name`, `description`, planned dates, `tags`, `relatedTaskIds`, and `parentTaskId`. Fields managed by the server (`id`, `lastUpdatedDate`, `latestStatus`, `isPaused`, `reasonForPause`, actual dates, and `childTaskIds`) are rejected on creation. `PATCH` accepts the editable creation fields plus `latestStatus` and `reasonForPause`; `tags` and `relatedTaskIds`, when supplied, replace those collections in full. Omitted patch fields remain unchanged. Use explicit `null` to clear a nullable field.

Use one error envelope everywhere:

```json
{
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "Request validation failed",
    "details": [{ "path": "plannedEndDate", "message": "Must be on or after plannedStartDate" }]
  }
}
```

Use these status codes consistently:

- `400` for malformed JSON or invalid path/query parameters;
- `404` when a task does not exist;
- `409` for a relationship cycle or a referenced task that prevents the requested state change;
- `422` for a well-formed request that violates validation or business rules; and
- `500` for an unexpected failure, with a generic response and the real error logged only on the server.

HTML form routes may reuse the same service methods. When the request has an `HX-Request` header, return only the fragment that HTMX needs to replace. Otherwise, return a full page or redirect after a successful form submission.

Use these HTML routes so the progressively enhanced interface also has a stable contract:

| Method | Route | Purpose |
| --- | --- | --- |
| `GET` | `/` | Render the task list, filters, and create form |
| `GET` | `/todos/:id/edit` | Render the edit form |
| `POST` | `/todos` | Create a task from form data |
| `POST` | `/todos/:id` | Update a task from form data |
| `POST` | `/todos/:id/delete` | Delete a task |
| `POST` | `/todos/:id/status` | Apply a lifecycle transition |

HTML forms use `application/x-www-form-urlencoded`. Tags are submitted as a comma-separated form field and normalized by the same service used by the JSON API. The web router translates form values into the service input type; it must not implement a second set of business rules.

## Step-by-step implementation

### 1. Prepare the repository

Select the declared Node version and create the package manifest:

```bash
nvm use
npm init -y
```

Install runtime dependencies:

```bash
npm install express better-sqlite3 zod nunjucks dotenv
```

Install development dependencies:

```bash
npm install --save-dev typescript tsx @types/node @types/express @types/better-sqlite3 @types/nunjucks vitest supertest @types/supertest eslint @eslint/js typescript-eslint prettier
```

Add the following scripts to `package.json`:

```json
{
  "scripts": {
    "dev": "tsx watch src/server.ts",
    "build": "tsc -p tsconfig.json",
    "start": "node dist/server.js",
    "test": "vitest run",
    "test:watch": "vitest",
    "lint": "eslint . && prettier --check .",
    "format": "prettier --write ."
  }
}
```

Configure `tsconfig.json` for strict TypeScript, Node's current module system, `src` as `rootDir`, `dist` as `outDir`, source maps, and JSON interoperability. Use two spaces, semicolons, and single quotes in Prettier. Configure ESLint with the recommended JavaScript and TypeScript rules.

Create `.gitignore` entries for at least:

```gitignore
node_modules/
dist/
.env
*.sqlite
*.sqlite3
*.db
coverage/
```

Create `.env.example` without secrets:

```dotenv
HOST=127.0.0.1
PORT=3000
DATABASE_PATH=./data/todos.sqlite3
```

Verification:

```bash
npm run build
npm run lint
```

Both commands must exit successfully before continuing.

### 2. Create the database migration

Create `migrations/001-create-todos.sql`. Keep the schema normalized: do not store tags or task IDs as comma-separated text or JSON.

```sql
PRAGMA foreign_keys = ON;

CREATE TABLE IF NOT EXISTS migrations (
  version INTEGER PRIMARY KEY,
  applied_at TEXT NOT NULL
);

CREATE TABLE todos (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  name TEXT NOT NULL CHECK (length(name) BETWEEN 1 AND 200),
  description TEXT,
  planned_start_date TEXT,
  planned_end_date TEXT,
  actual_start_date TEXT,
  actual_end_date TEXT,
  last_updated_date TEXT NOT NULL,
  latest_status TEXT NOT NULL DEFAULT 'planned'
    CHECK (latest_status IN ('planned', 'in_progress', 'paused', 'completed', 'cancelled')),
  reason_for_pause TEXT,
  parent_task_id INTEGER REFERENCES todos(id) ON DELETE SET NULL,
  CHECK (planned_end_date IS NULL OR planned_start_date IS NULL OR planned_end_date >= planned_start_date),
  CHECK (actual_end_date IS NULL OR actual_start_date IS NULL OR actual_end_date >= actual_start_date),
  CHECK (
    (latest_status = 'paused' AND reason_for_pause IS NOT NULL AND length(trim(reason_for_pause)) > 0)
    OR (latest_status <> 'paused' AND reason_for_pause IS NULL)
  ),
  CHECK (parent_task_id IS NULL OR parent_task_id <> id)
);

CREATE TABLE tags (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  name TEXT NOT NULL UNIQUE COLLATE NOCASE CHECK (length(name) BETWEEN 1 AND 50)
);

CREATE TABLE todo_tags (
  todo_id INTEGER NOT NULL REFERENCES todos(id) ON DELETE CASCADE,
  tag_id INTEGER NOT NULL REFERENCES tags(id) ON DELETE CASCADE,
  PRIMARY KEY (todo_id, tag_id)
);

CREATE TABLE related_todos (
  todo_id INTEGER NOT NULL REFERENCES todos(id) ON DELETE CASCADE,
  related_todo_id INTEGER NOT NULL REFERENCES todos(id) ON DELETE CASCADE,
  PRIMARY KEY (todo_id, related_todo_id),
  CHECK (todo_id < related_todo_id)
);

CREATE INDEX idx_todos_status ON todos(latest_status);
CREATE INDEX idx_todos_parent ON todos(parent_task_id);
CREATE INDEX idx_todo_tags_tag ON todo_tags(tag_id);
```

Store each related pair once, with the smaller ID in `todo_id`. The repository can query both columns to expose a symmetric relationship.

Implement `src/db/migrate.ts` to:

1. enable foreign keys for every connection;
2. bootstrap the `migrations` table before asking which versions have run;
3. read migration files in numeric order;
4. run each unapplied migration and its version insert inside one transaction; and
5. record its numeric version and an ISO timestamp in the `migrations` table.

Make startup create the parent directory for `DATABASE_PATH`, but never commit the generated database.

Verification: migrate a temporary empty database, inspect its tables, run migration a second time, and confirm the second run makes no changes and reports no error.

### 3. Add configuration and application errors

In `src/config.ts`, validate environment values once at startup with Zod. Export an explicit `AppConfig` rather than reading `process.env` throughout the codebase.

In `src/errors.ts`, create typed application errors for validation, not-found, and conflict cases. Add one final Express error middleware that converts known errors to the common error envelope and logs unknown errors without exposing stack traces or SQL messages.

Verification: add unit tests showing invalid ports and missing/empty database paths fail fast with readable messages.

### 4. Implement the repository

Create `src/db/todo-repository.ts` as the only module that knows SQL. Accept a database connection in its constructor so tests can inject an isolated database.

Implement these operations with prepared, parameterized statements:

- `create(input): Todo`
- `list(filters): Todo[]`
- `findById(id): Todo | null`
- `update(id, input): Todo | null`
- `delete(id): boolean`
- `replaceTags(id, tags): void`
- `addRelated(id, relatedId): void`
- `removeRelated(id, relatedId): void`
- `hasDescendant(id, possibleDescendantId): boolean`

The create and update inputs include the normalized tag and relationship changes required for that mutation. Use one transaction for the entire logical operation whenever it changes more than one table; do not commit the `todos` row before its tag or relationship writes have succeeded. Fetch tags, related IDs, child IDs, and the parent ID when mapping a database row to the public `Todo` object. Never interpolate input into SQL strings.

Repository tests must use a new in-memory SQLite connection for each test, apply the real migrations, enable foreign keys, and close the connection after the test. Cover CRUD, filtering, tag replacement, symmetric relationships, parent deletion, and rollback after a constraint failure.

Verification:

```bash
npm test -- tests/db/todo-repository.test.ts
```

### 5. Implement validation schemas

Create Zod schemas in `src/validation/todo-schemas.ts` for numeric positive route IDs, list query filters, create payloads, partial update payloads, and related-task path parameters.

Reject unknown body properties. Validate calendar dates strictly rather than relying on JavaScript's permissive date parsing. Add cross-field validation for date ordering and paused-state requirements. The patch schema must reject an empty object.

Keep validation at two levels: Zod checks the shape and local field relationships at the HTTP boundary, while the service checks rules that need current database state.

Verification: unit-test boundary values, invalid dates such as `2025-02-30`, unknown properties, empty patches, and every status/reason combination.

### 6. Implement the service layer

Create `src/services/todo-service.ts`. It coordinates validation that depends on stored tasks and calls the repository; it does not depend on Express.

Implement creation and update rules from the domain contract, automatic actual timestamps, tag normalization, existence checks for parents and related tasks, self-reference rejection, parent-cycle detection, not-found behavior, and one `lastUpdatedDate` refresh per mutation.

Inject both the repository and a `now(): Date` function. Tests can then use a fixed clock instead of weakening timestamp assertions.

Service tests must cover successful operations, every business-rule rejection, unknown IDs, relationship cycles, and simulated repository/database failures. Assert that a failed multi-table mutation leaves the old task intact.

Verification:

```bash
npm test -- tests/services/todo-service.test.ts
```

### 7. Build the JSON API

Create an Express router in `src/routes/api-todos.ts`. Route handlers should only parse inputs, call the service, and construct HTTP responses. Do not place SQL or business rules in handlers.

Add middleware to parse JSON with a small request-size limit. Implement every route in the HTTP contract and set `Content-Type: application/json` for JSON responses. Return a `Location: /api/todos/:id` header after creation.

Route tests should construct the application with a temporary database and call it through Supertest. For every REST operation cover success, validation failure, not found where applicable, and an injected database failure that produces a generic `500` without leaking the internal message.

Also test malformed JSON, unsupported content types, filters, error-envelope consistency, and relationship conflicts.

Verification:

```bash
npm test -- tests/routes/api-todos.test.ts
```

### 8. Build the HTML and HTMX interface

Configure Nunjucks in `src/app.ts` and serve `public/` as static assets. Do not require client-side JavaScript other than HTMX.

The full `index.njk` page should contain:

- a create/edit form;
- status and tag filters;
- a task list with empty-state text;
- controls to edit, delete, start, pause, resume, complete, or cancel a task; and
- visible tags, dates, parent/children, and related tasks.

Split reusable markup into the partials shown in the target tree. Point HTMX actions at HTML routes, select explicit targets, and choose swaps that leave valid markup after create, update, and delete. Return form markup with inline field errors and HTTP `422` when a submission is invalid.

Include the current minified HTMX release as a version-pinned local asset under `public/` or use a version-pinned CDN URL with integrity and cross-origin attributes. Do not use an unversioned CDN URL.

Keep basic non-HTMX behavior working: normal form submissions redirect back to `/`, and task actions use real forms rather than click handlers on non-interactive elements.

Add accessible labels, keyboard-usable controls, a visible focus state, a page heading, table/list semantics, and an `aria-live` status region for updates. Make the layout usable on narrow screens.

Web-route tests must cover full-page rendering, fragment responses with `HX-Request: true`, successful form actions, validation markup, filters, and a non-HTMX redirect.

Verification:

```bash
npm test -- tests/routes/web-todos.test.ts
```

Then run the server and manually verify create, edit, filter, lifecycle transitions, and delete with browser developer tools showing no full-page navigation for HTMX actions.

### 9. Compose and start the application

In `src/app.ts`, export a `createApp` function that accepts explicit dependencies and returns the configured Express application. Register routes in this order:

1. request parsing and static assets;
2. `/health`;
3. JSON routes;
4. HTML routes;
5. a not-found handler; and
6. the final error handler.

In `src/server.ts`, load and validate configuration, open the database, run migrations, construct the repository and service, create the app, and start listening. Handle `SIGINT` and `SIGTERM`: stop accepting requests, close the database, and exit cleanly.

The health route must verify the database with a lightweight query such as `SELECT 1` and respond with:

```json
{ "status": "ok" }
```

Return `503` with the generic error envelope when the database readiness check fails.

## Definition of done

The project is in its final state only when all of the following are true:

- a fresh clone can be set up using only this README and `.env.example`;
- migrations create a new database and are safe to rerun;
- every route in the HTTP contract behaves as documented;
- all domain rules are enforced even when requests bypass the browser UI;
- SQL statements that include user input are parameterized;
- multi-table writes are transactional;
- REST tests cover success, validation, not-found, and database-failure paths;
- tests use temporary or in-memory databases and never touch developer data;
- the UI works with and without HTMX enhancement;
- error responses never expose stack traces, SQL, or filesystem paths;
- `npm run lint`, `npm run build`, and `npm test` all pass; and
- generated databases, `.env`, build output, dependencies, and coverage output are not tracked by Git.

## Suggested commit sequence

Keep each milestone reviewable. A useful sequence is:

1. `chore: configure typescript tooling`
2. `feat: add sqlite schema and migrations`
3. `feat: add todo repository`
4. `feat: enforce todo business rules`
5. `feat: add todo REST API`
6. `feat: add HTMX todo interface`
7. `test: cover todo application workflows`
8. `docs: document setup and verification`

Do not commit generated databases or combine unrelated formatting changes with a functional milestone.
